# 后台搜索与筛选收纳：方案构思与预览交接

日期：2026-10-29；代码基线：`3fac280`；关联 [issue #274](https://github.com/ZAFU-PCHospital/zafu-pchospital-web/issues/274)

本文交给下个会话制作可交互预览，尚未选定生产方案。目标是让数据成为首屏主体，同时让用户随时知道“现在看的是哪些数据”。不是把所有控件藏得越深越好。

建议先预览 **A 的效率、B 的简洁、C 的直接、D 的任务感**，使用相同数据比较，不只看空白状态。优先考虑 A；如果希望搜索也真正收起来，优先看 B。D 更适合维修审核，不必强求五个页面完全同形。

| --------------------------- | ------------------------------------ | ---------------------------------- |

## 3. A：短搜索框 + 筛选浮面板（优先推荐）

**感觉：轻量的表格工具，搜索随手可用，筛选只在需要时出现。**

```text
成员管理                                      新增成员
[ 搜索成员………… ] [搜索] [筛选 2 ▾] [高级]
状态：启用 ×   角色：维修员 ×                   清除筛选
共 128 名   批量操作 · 导出
────────────────────────────────────────────────────
姓名       班级       角色       状态 …
```

数字、角色与姓名均为预览示意，不代表线上数据。

- 搜索框桌面宽约 16–20rem，取消外层整块卡片，工具区只用细分隔线与留白
- 筛选按钮打开锚定浮面板，放状态、角色等快捷条件；面板宽约 20–24rem，底部“取消 / 应用”。高级入口沿用现有弹窗，避免在小浮层里编辑复杂运算符
- 搜索提交仅更新关键字；筛选应用仅更新对应快捷字段，彼此不提交对方未完成的草稿
- 收起后保留生效标签，条件数只统计非空快捷筛选和列级条件，不含搜索、排序、分组；搜索值在输入框里可见
- 手机搜索独占一行，下方保留“筛选 / 高级”；筛选改用现有模态窗口承载，不把桌面浮层挤到屏幕外
- 审计页不渲染搜索，直接显示“筛选 / 高级”；邀请码浮面板只放状态，保持简单

美观重点：搜索区不铺强调色；仅有条件的筛选按钮使用 `accent-wash` 和文字计数，标签用轻描边。新增按钮保留主动作层级。

代价：桌面浮面板需要定位、点击外部关闭和键盘处理；高级与快捷是两个入口，需要清楚命名。适合找人、找维修记录等高频搜索，不满足“搜索完全消失”的极简偏好。

## 4. B：一个“搜索与筛选”入口 + 查询摘要

**感觉：最安静，默认看数据，需要时才进入查询。**

```text
成员管理                                      新增成员
共 128 名   [⌕ 搜索与筛选]          批量操作 · 导出
────────────────────────────────────────────────────
姓名       班级       角色       状态 …

有条件时：
[⌕ 张同学 · 状态：启用 · +2] [清除筛选]
```

- 默认是有文字的按钮，不是孤零零放大镜；点击打开统一查询窗口
- 桌面预览可用右侧覆盖式抽屉，建议宽 28rem、上限不超过视口；内容按“搜索 / 常用筛选 / 高级条件 / 排序与分组”排列，后两组折叠
- 手机使用全宽模态面板，标题与应用区可见、正文滚动；软键盘弹出后输入和提交仍可达
- 所有修改先进入同一草稿，底部“取消 / 应用”；应用后收起。分组有结果需要查看时按现有行为保留窗口，不能把分组计数藏没了
- 摘要默认最多展示两个条件，再用“+N”打开完整窗口；完整内容可通过键盘或点击查看，不能只靠 hover tooltip
- 审计页入口叫“筛选”，窗口不出现搜索区域

美观重点：列表顶端只有一条平直工具栏；有条件时入口从“动作按钮”变成可读的查询摘要。抽屉以 `surface-1`、细边界建立层次，不添加大面积装饰。

代价：每次开始搜索多一次点击；抽屉会遮住部分表格。当前 `QueryDialog` 不含快捷字段，不能只换个 CSS 就完成统一草稿。要扩展现有弹层能力，避免抽屉里再叠一个高级弹窗。

建议作为最值得与 A 对照的方案；若抽屉成本过高，先用既有居中 `AdminModal` 验证交互，再判断侧置是否确有收益。

## 5. C：工具栏下的折叠查询带

**感觉：操作直接，收起很薄，展开仍然是一张清楚的表单。**

```text
共 128 名  [搜索与筛选 ▾]              导出 · 新增成员
状态：启用 ×                          清除筛选
────────────────────────────────────────────────────
列表…

展开后：
共 128 名  [搜索与筛选 ▴]              导出 · 新增成员
关键字 […………]  状态 [全部 ▾]  角色 [全部 ▾]
[应用] [高级] [取消]
────────────────────────────────────────────────────
列表…
```

- 默认折叠；点击在原位展开一条查询带，桌面字段紧凑排列，手机单列
- “应用”提交后折叠；“取消”丢弃本次草稿；点击收起按钮仅收起并保留当前会话草稿，再展开仍能继续
- 草稿存在时入口附短文本“未应用”，生效标签始终只来自已提交状态
- 展开允许由用户触发的列表下移，不使用自动滚动；关闭前若焦点在内部，返回触发按钮。隐藏字段不得继续出现在 Tab 顺序中
- 高级筛选保持现有弹窗，避免在展开区内继续堆复杂条件

美观重点：展开区用上下细线收边，不再套全宽大卡片；字段标签紧凑，主要空间仍留给列表。

代价：展开时依然占首屏高度，手机尤其明显；不适合反复一边改条件一边对照表格。实现相对最简单，适合希望低成本改善当前布局的选择。

## 6. D：常用状态页签 + 按需搜索与更多条件

**感觉：进入一个工作队列，先处理任务，再精确查找。**

```text
维修审核
[全部] [待审核] [已通过] [已退回]      [搜索] [更多筛选]
分类：软件问题 ×                               清除筛选
共 36 条                              批量操作 · 导出
────────────────────────────────────────────────────
设备       故障       提交人       状态 …
```

- 页签只映射已有 `status` 参数，保留默认状态，不擅自把“待审核”设为新的默认值
- 点击“搜索”在工具栏下露出短搜索输入；Enter / 搜索按钮应用。有关键字时保留摘要，收起不会清空
- 分类等进入“更多筛选”，高级条件仍复用既有入口；切换状态只改变快捷状态，不重置搜索、分类和排序
- “全部”表示取消快捷状态限制；仍有列级状态条件时必须展示标签，避免用户误以为已看全部数据
- 不显示页签计数，除非现有数据明确提供同口径计数；不能把当前分页条数当成各状态总数
- 手机用短状态选择器替换过长页签，搜索与更多筛选保持文字入口

美观重点：页签用细下划线或轻底色，不做一排大色块；“待审核”等状态不是营销标题，保持工作区字号。

代价：跨页面一致性较弱；招募同时有审核状态和开通状态，不能都铺成页签。建议只在维修审核预览 D；成员、邀请码及审计优先 A/B，不把常用队列做成未经确认的新业务视图。

## 7. 怎么选

| 维度             | A 短搜索 + 浮面板  | B 统一入口     | C 折叠查询带       | D 状态页签 |
| ---------------- | ------------------ | -------------- | ------------------ | ---------- |
| 默认首屏收纳程度 | 中高               | 最高           | 高                 | 高         |
| 高频搜索效率     | 最好               | 多一次打开     | 多一次展开         | 多一次展开 |
| 多条件集中编辑   | 一般               | 最好           | 良好               | 一般       |
| 一边编辑一边看表 | 较好，浮层局部遮挡 | 一般，抽屉遮挡 | 可见但会下移       | 较好       |
| 相对改造成本     | 中                 | 中高           | 低                 | 中         |
| 最适用           | 成员、邀请码       | 招募、审计     | 保守改造、低频查询 | 维修审核   |

这些是设计判断，不是用户研究结论。首轮不做自定义查询语法、AI 搜索、保存视图、可拖拽筛选栏或自动随滚动隐藏工具栏，避免为收纳增加学习和维护成本。

## 8. 四案共用的交互底线

1. **关闭不等于清空**：已应用条件一直有效。收起时有可读摘要，不能只亮一个小圆点；无条件时不留空标签行
2. **草稿与结果分开**：摘要、总数、导出只对应已应用条件；请求失败保留旧列表并标记结果尚未更新，不能把旧数量标为新条件的结果
3. **明确清除范围**：“清除筛选”清空关键字、快捷字段和列级条件，保留排序/分组；“重置查询”沿用现有 `query.reset()` 的完整语义。此处是拟议的文案与动作区分，预览必须展示差别，不能把新文案直接绑到旧 reset 上
4. **条件可以逐条移除**：快捷条件标签与高级条件分别绑定自己的状态字段；删除搜索不清空状态，删除高级条件不清空快捷字段。排序/分组单独标识，不计入筛选数量
5. **保持现有能力**：列宽、表头排序、多排序优先级、分组计数、批量操作、导出和加载更多仍可达。换查询沿用现有页面清理选择的规则；仅开关面板不改变选择
6. **保持隐私白名单**：姓名、QQ、手机号等自由文本不写 URL、localStorage 或查询历史。关闭面板保留内存状态，刷新后的恢复范围沿用既有规则
7. **主题与可访问性**：沿用 `Button`、`Icon`、`.field__input`、语义令牌和现有焦点环；触屏目标以既有 46px 为起点。弹层处理 Esc、焦点返回、滚动锁；折叠触发器有 `aria-expanded` / `aria-controls`
8. **长内容也要成立**：标签单项截断但可点击查看完整值，超过两行可收为“其余 N 项”；清除按钮保持可达。不让标签无限堆高，也不使用只能横向拖动才能看到的清除入口

## 9. 下一个会话的预览任务

可直接把以下任务交给下个会话：

> 阅读本文、AGENTS.md 与设计规范，在独立分支实现 A/B/C/D 可切换的本地交互预览。先检查当前代码是否仍与本文基线一致。暂不替换生产 `AdminTableQuery`，不修改 API、Schema 或权限，不发布、不部署。沿用项目样式和组件，使用明确标注的虚构数据。需要隔离预览路由时只放开发环境，不加入公开导航，生产不可访问。预览完成后交回本地访问方法、比较结果与剩余问题，由用户选方案后再做正式接入。

预览范围：

- 成员管理呈现 A/B/C 的同数据对照；维修审核呈现 A/D 对照；另用招募四字段与审计无搜索模式检查 B 的承载能力，不必复制五套完整后台
- 每案有默认、已应用搜索及多个条件、编辑未应用、长标签、零结果、刷新中与失败保留旧数据状态；所有方案共用同一份状态样例与列表
- 主操作可点通：打开、输入、应用、取消、收起、移除单项、清除筛选、重置查询。请求可模拟延迟与失败，页面明确这是预览，不连接真实写接口
- 先在预览局部组合已有组件，确认方案后再抽取共享 API；不提前把四套候选分支塞进生产组件

比较方法：

| 检查       | 做法                                                                                                             |
| ---------- | ---------------------------------------------------------------------------------------------------------------- |
| 首屏收益   | 1440×900、1280×800 下记录查询区高度、表格首行 Y 坐标、可见记录数；同一数据与页面壳比较旧版及四案，不预填虚构基线 |
| 窄屏       | 390×844，并补 320px 溢出断言；确认抽屉、输入法软键盘、长标签及提交按钮可用                                       |
| 操作成本   | 分别记录“搜索某人”“状态 + 角色”“移除一项”“恢复默认”的点击与键盘步骤                                              |
| 状态正确性 | DOM 断言检查摘要来自应用值、取消不生效、关闭不清空、删除不误伤其他条件、无搜索页不出现输入框                     |
| 视觉       | 浅/深色各看默认与展开的代表视图；只有需判断观感时截图，临时产物放仓库外并按工程规则清理                          |
| 正式接入前 | 再回归真实 URL 白名单与后退恢复、导出口径、分组结果、选择清理、迟到请求及焦点；模拟预览通过不等于业务回归通过    |

本轮只完成构思文档。没有浏览器度量、成品截图或交互测试；没有修改公共契约、组件 API、Migration 或依赖。本文尺寸是预览起点，最终用实际可用宽度和操作结果决定。
